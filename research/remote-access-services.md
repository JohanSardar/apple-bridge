**Public remote access for Apple Bridge — researched 2026-10-27** (external survey by Codex GPT-6 Astra; Apple Bridge internals, spot-checks and the recommendation by Claude)

The best fit is a developer-operated TLS-passthrough relay, following Nabu Casa, with a stable hostname and an individual certificate/private key on each Mac. A managed alternative is ngrok's embedded Go SDK with TLS endpoints and negotiated E2E pricing; Cloudflare named tunnels simplify operations if Cloudflare seeing plaintext is acceptable. This is external-source research, not a deployment test. The **Apple Bridge today** paragraphs below were checked against the code on `main` at 396175cc. “E2E” below means HTTPS from the remote client to the Mac, excluding the relay from plaintext; it does not hide data from Claude/ChatGPT when they call a tool. Architectural conclusions and cost calculations are explicitly estimates/inferences. Unverified means the reviewed primary sources did not establish the claim, not that the feature is absent.

**Cost and compatibility conventions.** Prices below are USD/month unless marked otherwise, before tax, domain registration, engineering and support. Fleet sizes mean one independently addressable Mac per user; a shared account's quotas do not multiply by user count. Estimates use 730 hours/month where hourly billing matters. “TCP-inferred” streaming compatibility means a byte-transparent TCP tunnel should carry HTTPS, WebSocket and SSE without parsing them; actual connector behavior, idle timeouts, reconnects and throughput remain unverified. The [MCP transport specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) defines Streamable HTTP using HTTP POST with JSON or SSE replies. It does not make an arbitrary TCP endpoint, WebSocket endpoint or private overlay directly usable as a public HTTPS MCP URL. Self-hosted projects have no SaaS bandwidth allotment: infrastructure capacity and the operator's limits determine it.

**Apple Bridge today: sign-in for connectors already exists.** The Mac serves its own OAuth authorization server and protected MCP resource ([SPEC §23.6](../design/SPEC.md), `internal/web/oauth_*.go`).
- **Discovery:** `/.well-known/oauth-protected-resource` and `/.well-known/oauth-authorization-server`.
- **Registration:** dynamic client registration at `/oauth/register`.
- **Flow:** PKCE S256 only, `token_endpoint_auth_methods_supported: none`, issuer identification (`iss` on the redirect, RFC 9207), and an exact `resource` match against `<origin>/mcp` (RFC 8707).
- **Consent:** a page gated by the owner's passkey session. The owner picks `read`, `approve` (each command waits for the owner) or `full`, plus source scopes.
- **Tokens:** access tokens last 1 hour. Refresh tokens rotate and last 90 days, and can be revoked from the Agents list. Every agent gets a 90-day activity log.

Feature `web.agents` is `done` with sim and browser coverage only. No run yet against a real Claude Code, claude.ai or ChatGPT connector over a public URL.

**Apple Bridge today: agents can already keep their own copy.** Public routing gives agent tokens `/mcp` and `/v1/*`, including `records.query` paging and the `GET /v1/changes` SSE stream ([SPEC §23.5](../design/SPEC.md)). A remote Claude Code can read, act and mirror data into its own database without the replica feed, which stays optional.

**Apple Bridge today: the only missing layer is reachability.** `bridge remote on` puts the web app, `/oauth/*`, `/v1/*` and `/mcp` on one public HTTPS host. Its only backends are Tailscale Funnel:
- **`system`:** passes real checks from Ubuntu (2026-10-21).
- **`embedded`:** `limited`, because the end user must sign in to Tailscale and enable Funnel.

The seam is a backend switch in `internal/remote` (`Remote.serve`). A backend that hands `bridge` a `net.Listener` of TLS connections terminated in-process plugs straight in, as embedded Funnel does with `ListenFunnel`, and keeps host pinning, CSP, rate limits and the passkey relying-party ID. ngrok-go and a home-built SNI relay client both fit that shape. A backend that terminates TLS elsewhere must reuse the capability-protected forwarding path of `system` mode, and its operator can read traffic.

**Apple Bridge today: gaps found.**
- **Client ID Metadata Documents:** not supported. ChatGPT prefers them; Claude Code and claude.ai accept dynamic registration.
- **Advertised scopes:** the protected-resource metadata lists only `messages:read` in `scopes_supported`, while the authorization server accepts all 12 source scopes.
- **Stable hostname:** passkeys bind to the serving hostname, so a per-user hostname must be stable from day one, and enrollment must work on the public origin.
- **Bluetooth:** cross-device passkey sign-in (phone QR) needs Bluetooth on the visiting computer. An "approve this sign-in from your phone" fallback would cover computers without it.

**Our relay: SNI-routing TLS passthrough.** Proposed design, derived from [SniTun's connection flow](https://github.com/NabuCasa/snitun): Bridge enrolls once over a control-plane API, obtains a random stable hostname and narrowly scoped relay credential, and maintains an outbound authenticated multiplexed connection. Public DNS points device names at shared relays; port 443 reads ClientHello SNI, maps the name to its authenticated Mac session, then forwards bytes without TLS termination. Serve the full origin, including discovery, OAuth and consent, rather than only `/mcp`. Mac-generated private keys stay on the Mac. This supports conventional browsers and MCP clients with no visitor install; it also preserves WebSocket/SSE by construction. Implement reconnection/backpressure, per-device concurrency/byte limits, hostname ownership, token revocation and a kill switch. An SNI router sees hostname/IP/timing/volume, not HTTP content. Encrypted ClientHello and HTTP/3 need separate design; initial scope should be ordinary TCP HTTPS with visible routing SNI, not an unverified claim of universal transport support.

**Certificates: DNS-01 or TLS-ALPN-01.** [Let's Encrypt challenge documentation](https://letsencrypt.org/docs/challenge-types/) supports DNS-01 using `_acme-challenge` TXT records, including delegated CNAME/NS validation, and TLS-ALPN-01 on port 443. Proposal: generate a unique private key and CSR on each Mac; let a tightly scoped control-plane service publish only that device's DNS challenge. Never ship a zone-wide DNS credential or shared wildcard private key. Alternatively route TLS-ALPN-01's SNI and `acme-tls/1` handshake through the relay to the Mac; this requires the Mac online for validation and an unmodified TLS handshake. DNS-01 avoids needing the device publicly reachable for challenge validation, but the Mac still needs its certificate installed before serving clients. Automated renewal/retry after sleep and expiry is essential. A wildcard cert copied to every Mac would let one compromised Mac impersonate others; individual keys avoid that shared-key failure.

**Let's Encrypt limits and PSL.** [Current limits](https://letsencrypt.org/uk/docs/rate-limits/): **300 new orders/account/3 hours**, **50 certificates/registered domain/7 days across all accounts**, and **5 certificates/exact identifier set/7 days**. ARI-coordinated renewals are exempt; rate-limit overrides take a few weeks to process. Therefore 100 or 10,000 initial distinct device certs under one ordinary registered domain need a planned override/rollout, not one ACME account per Mac to evade the domain limit. [PSL guidelines](https://github.com/publicsuffix/list/wiki/guidelines) require a PRIVATE-section PR, an authorized domain owner, `_psl` TXT proof, at least two years' remaining registration and a genuine mutually untrusting tenant namespace. Requests solely to bypass CA limits are rejected; small/beta projects may be declined. There is **no review-time SLA**, and downstream propagation depends on browser/OS/CA updates. No fixed “two weeks” or “three months” promise is verified. Seek a CA override for launch; pursue PSL for tenant isolation once eligible.

**Certificate Transparency and trust boundary.** [Nabu Casa](https://support.nabucasa.com/hc/en-us/articles/26508882007581-Remote-access-Security-aspects) explicitly uses CT as an independent check of certificates for an instance. [Cloudflare CT monitoring](https://developers.cloudflare.com/ssl/edge-certificates/additional-options/certificate-transparency-monitoring/) alerts on certificates issued for a domain. Proposal: record expected device certificate fingerprints/issuance and monitor unexpected certificates, protect DNS/ACME administration, and use opaque hostnames without owner identifiers. CT makes certificate names observable, so a random URL is not authentication. TLS passthrough excludes an honest relay from plaintext, but a compromised operator controlling DNS/validation could obtain a replacement certificate and actively intercept future connections. CT is detection, not prevention or client pinning; ordinary Claude/ChatGPT connectors do not provide a verified per-device pinning flow. This is the practical limit of the desired E2E claim.

**Hosting and bandwidth model.** [DigitalOcean's price sheet](https://www.digitalocean.com/pricing/droplets) lists **$6/month for 1 GiB RAM plus 1,000 GiB transfer**, **$12 for 2 GiB plus 2,000 GiB**, and **$18 for 2 vCPUs/2 GiB plus 3,000 GiB**. [Bandwidth billing](https://docs.digitalocean.com/platform/billing/bandwidth/) pools Droplet allowances, charges **$0.01/GiB extra egress**, and makes ingress free. Illustrative budgets, **not measured capacity**: two $6 relays = **$12/month at 100 Macs** with 2,000 GiB allowance; six $18 relays = **$108/month at 10,000 Macs** with 18,000 GiB. Assume 1 GiB combined application traffic/user/month: 100 or 10,000 GiB fits those pools before overhead. At 10 GiB/user and 10,000 users, 100,000 GiB gives **$820 overage + $108 = $928/month**. Bytes passing through a relay are received then sent; do not count free ingress as billable egress twice, but include both application directions, encapsulation and any inter-region forwarding. These examples exclude database/control plane, monitoring, failover headroom and staff; connection/load testing could require more machines. No claim that $108 buys a production SLA.

**OpenAI Secure MCP Tunnel — 2026 provider-specific alternative.** [Official documentation](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels) supports private MCP access from ChatGPT, Codex and the Responses API. A local `tunnel-client` polls outbound HTTPS, forwards JSON-RPC to local stdio/HTTP servers and returns responses, including intermediate SSE. This **does reach a private Mac**, unlike an auth-only provider. It is an application-level OpenAI endpoint, not browser-to-Mac TLS passthrough or a generic web/REST/WebSocket URL. Setup requires a tunnel ID, runtime API key and Platform-organization/ChatGPT-workspace permissions/associations; developer-managed consumer-fleet redistribution and SDK embedding are unverified. Defaults: **1,000 tunnels per workspace/organization, 600 requests/minute per tunnel/calling application, 10 MiB serialized envelopes, 120-second absolute request deadline**, 1,000 queued requests. Published 100/10,000-user bandwidth/pricing and self-hosted service availability are unverified. Public plugin submission/distribution is explicitly unsupported through this route; it needs a public HTTPS endpoint. Useful optional OpenAI-specific integration, not the universal access layer.

**Anthropic MCP tunnels — June 2026 research preview.** [Official overview](https://platform.claude.com/docs/en/agents-and-tools/mcp-tunnels/overview) uses outbound cloudflared plus a local routing proxy; **inner TLS from Anthropic to that proxy** prevents Cloudflare from reading payloads, while OAuth remains separate. Documented consumers are **Managed Agents and the Messages API**, not proof of compatibility with arbitrary browsers, Claude Code HTTP URLs or claude.ai/mobile custom connectors. Deployment targets Docker Compose/VM or Kubernetes, with Console/manual enrollment or workload-identity federation; no single-binary Mac embedding was verified. [Reference](https://platform.claude.com/docs/en/agents-and-tools/mcp-tunnels/reference) identifies beta `mcp-tunnels-2026-06-22`, tunnel API operations and customer-registered CA certificates. The account is the customer's/developer's Anthropic organization, with organization-bound access; it is not an anonymous public hostname. Custom public domains, general WebSocket/SSE guarantees, 100/10,000-device prices, bandwidth quotas, redistribution rights and self-hosting the managed service remain unverified. It demonstrates how a cooperating MCP client can use private CA trust and E2E over Cloudflare, a capability ordinary public browsers do not automatically share.

**Cloudflare remote MCP / workers-oauth-provider.** [October 2026 v1](https://developers.cloudflare.com/changelog/post/2026-10-01-workers-oauth-provider-1x/) separates an authorization Worker from resource-server Workers and supports CIMD, issuer identification and older DCR clients. This solves cloud auth/hosting, not outbound connectivity from a NATed Mac. A Worker could front a Mac **after** adding Tunnel or a custom outbound channel, but normal Worker HTTP processing terminates TLS in Cloudflare and can read tool content. Bridge already has its owner consent and OAuth model; replacing it adds integration work without removing the need for a relay. A service binding connects Workers, not a private home Mac. Do not confuse a deployable remote-MCP example with a generic device-tunneling SDK.

**Stytch.** [Connected Apps](https://stytch.com/connected-apps) offers OAuth 2.1/DCR and remote MCP authorization; [existing-auth integration](https://changelog.stytch.com/announcements/2025-09-09-stytch-connected-apps-for-existing-auth-systems) can avoid replacing the entire login stack. It could serve as Bridge's authorization server while the resource server stays on the Mac, but no outbound Mac tunnel/public URL service was verified. Therefore useful for outsourced identity, not a substitute for reachability, and not needed merely because this is MCP.

**WorkOS.** [AuthKit's MCP integration](https://workos.com/blog/secure-mcp-servers-workos-authkit-xmcp) documents OAuth/CIMD integration with MCP servers. Hosting location is not intrinsically restricted to a cloud VM: a reachable Mac can validate its tokens. No native Mac NAT traversal or stable public relay was verified. Existing Bridge passkey consent and per-agent approval would still need explicit integration rather than assuming identity-provider scopes reproduce them.

**Descope.** [MCP gateways](https://docs.descope.com/mcp/gateways) can front remote MCP servers with authentication, routing, token exchange and tenant policy; the Agent Gateway is early access. A gateway can front the Mac if an upstream route exists, but a public URL to the gateway does not create that route. No bundled Mac outbound connector was verified. Acting as an HTTP/MCP proxy introduces a plaintext processing party; using Descope only as authorization server need not. It is a managed front end, not documented relay-blind connectivity.

**Auth0.** [Auth for MCP GA, May 6, 2026](https://auth0.com/blog/auth0-auth-for-mcp-servers-generally-available/) covers auth, CIMD registration, resource identifiers and on-behalf-of exchange. It can authorize any appropriately reachable resource server, including a tunneled Mac. It does not document making that Mac publicly reachable; Apple's local data still requires Bridge. Adding it does not solve the present missing layer.

**Smithery.** [Current publishing documentation](https://smithery.ai/docs/build/publish) says its gateway proxies a **public HTTPS upstream**, using Streamable HTTP and OAuth, while local stdio distribution uses a downloadable MCPB bundle. Thus it can front Bridge only after reachability is solved; the local bundle path installs software on the consuming device and misses the requirement. No production per-owner Mac reverse tunnel was verified. Its gateway processes MCP rather than preserving TLS to the Mac.

**Composio.** [Custom MCP](https://docs.composio.dev/docs/extending-sessions/custom-mcp) explicitly requires deploying the server at a public HTTPS URL, then registering/syncing it; the feature is experimental. It can front/aggregate the tunneled Mac, but does not supply the tunnel. [Hosted session endpoints](https://docs.composio.dev/docs/sessions-via-mcp) do not expose custom tools that run inside the local SDK process. Moving tool execution through Composio changes data/credential custody rather than solving relay-blind reachability.

**Pipedream.** [Hosted MCP for developers](https://mcp.pipedream.com/developers) provides cloud tools for thousands of apps/APIs with managed integration. An HTTP workflow could call an already reachable Bridge, but arbitrary NATed Mac ingress and a shipped per-device reverse tunnel are **unverified**. It is not evidence of an iCloud-on-the-owner's-Mac relay; cloud workflows would process tool content.

**Klavis.** [The official repository](https://github.com/Klavis-AI/klavis) describes hosted/open-source MCP integrations and authentication. Deploying its servers or using Strata is a cloud integration path, not verified public ingress to a user's Mac. A custom integration can call Bridge once connectivity exists; a product-ready Mac tunnel, certificate service and relay-blind transport remain **unverified**.

**mcp-remote.** [The project](https://github.com/punkpeye/mcp-remote) adapts a local stdio-only client to an existing remote MCP server and handles OAuth. It runs on the **client** machine, does not publish a server behind NAT, and conflicts with “nothing else installed on the other device.” Not needed for native HTTP-capable Claude Code or hosted connectors.

**Peer-to-peer WebRTC.** [WebRTC documentation](https://webrtc.org/getting-started/peer-connections) requires signaling/ICE negotiation and STUN/TURN; a browser app could connect to a Mac WebRTC implementation over an encrypted data channel, with TURN fallback. This can reduce direct-path bandwidth, but needs a custom browser protocol and identity binding, and TURN still costs relay bandwidth. The [standard MCP transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) are stdio and Streamable HTTP; custom transports require both ends to implement them. Inference confirmed by the documented client interfaces below: `claude mcp add --transport http` and hosted URL connectors do not negotiate WebRTC for arbitrary MCP URLs. A public HTTPS-to-WebRTC gateway could translate, but then becomes the necessary relay and normally a TLS endpoint. WebRTC is an optional optimization for our own web app, not the universal MCP access layer.

**Claude Code compatibility.** [Official MCP documentation](https://code.claude.com/docs/en/mcp) supports `claude mcp add --transport http apple-bridge https://DEVICE.example.com/mcp`, OAuth sign-in, DCR, CIMD and preconfigured credentials. Its default callback is `http://localhost:PORT/callback` with an available port; `--callback-port` pins one. Version 2.1.229 used `127.0.0.1` instead; 2.1.231 restored `localhost`. Register/validate the exact callback supplied rather than accepting arbitrary redirects. Claude Code can reach local/private servers when its own network permits, so “public HTTPS” is the universal-URL product path, not every possible CLI or provider-specific tunnel deployment. Its documented HTTP interface does not require a WebRTC client. Trusted public certificates avoid custom trust configuration on every consuming machine; self-signed-certificate bypass is not a product solution.

**claude.ai / Claude mobile.** [Connector-building guidance](https://support.anthropic.com/en/articles/11503834-building-custom-integrations-via-remote-mcp-servers) documents Streamable HTTP and legacy SSE, OAuth/DCR or supplied OAuth client credentials, callback **`https://claude.ai/api/mcp/auth_callback`**, and mobile use of connectors added on the web. [Current setup](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp) additionally offers Claude's published identity, automatic registration or a custom OAuth client. [Surface guidance](https://support.claude.com/en/articles/11725091-when-to-use-desktop-and-web-connectors) distinguishes public-URL remote connectors from local MCP. For ordinary URL connectors, the URL must be reachable from Claude's infrastructure, not just the phone's LAN; the separately documented API tunnel is not evidence that claude.ai supports that private route. Treat public HTTPS with a publicly trusted chain as the deployment requirement; an explicit private-CA trust-upload mechanism was not verified. Preserve public discovery/token endpoints and browser-accessible consent, without a tunnel-provider login wall.

**ChatGPT compatibility (public URL path).** [Official authentication documentation](https://developers.openai.com/plugins/build/auth) requires HTTPS discovery, OAuth code flow with advertised PKCE **S256**, canonical resource/audience handling and token auth-method metadata. CIMD is preferred when available; DCR and predefined clients remain supported. **Do not assume one callback for every connection:** absent RFC 9207 issuer identification, current ChatGPT uses **`https://chatgpt.com/connector/oauth/{callback_id}`**; eligible servers advertising issuer identification and returning matching `iss` on success/error can use **`https://chatgpt.com/connector_platform_oauth_redirect`**, also retained by older published servers. Use the exact redirect shown in server management/registration. A publicly reachable HTTPS origin with a trusted certificate is the suitable deployment; private-CA enrollment is unverified. Its OpenAI-managed mTLS client certificate is optional client identification, not a replacement for user OAuth. TLS-terminating tunnels prevent the Mac directly validating that original client TLS certificate, whereas passthrough preserves it. Bridge already advertises PKCE S256, DCR and issuer identification and binds `resource` exactly; CIMD is the missing piece (see **Apple Bridge today: gaps found**).

**Cross-tunnel interoperability and passkeys.** Proposed acceptance checks, derived from the [MCP authorization rules](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization): publish the entire public origin; ensure issuer/resource/redirect URLs use its stable HTTPS name; preserve `Authorization`, `WWW-Authenticate`, methods and streaming responses; validate OAuth redirect URIs; return a real 401 challenge, not a tunnel HTML login page. Free ngrok/Pinggy/zrok and Microsoft interstitials can interrupt discovery or consent depending on request classification; they are a risk, not proof every machine request fails. Named Cloudflare needs streaming headers and no incompatible Access/challenge layer. Raw TCP/TLS tunnels avoid HTTP rewrites but still need trusted certs and reconnection. Bridge's passkey consent also needs review: [WebAuthn RP IDs are scoped to the calling origin/domain](https://www.w3.org/TR/webauthn-3/#rp-id). A localhost-enrolled passkey cannot simply be assumed usable at a new public hostname; provide authorized remote-origin enrollment/account recovery. Stable URLs prevent repeated consent/resource-identity changes, but the Mac must remain awake and reachable.

**Recommendation**

1. **Prove the connector experience now, on the owner's Mac, with what already works.** Turn on `bridge remote on` (system Funnel). Add `https://<host>/mcp` in Claude Code (`claude mcp add --transport http`), as a claude.ai custom connector (which also reaches Claude mobile), and in ChatGPT. Sign in through the passkey consent page, then send a tagged message to the owner's own handle. This is the first real end-to-end proof of the sign-in path and needs no new infrastructure. Fix what it finds, starting with the advertised scopes and CIMD.
2. **For other users, build a Nabu Casa-style relay as a third `internal/remote` backend.**
   - **Mac side:** the Mac enrolls once and gets a random, stable hostname under a domain we own. It keeps one outbound multiplexed connection, and gets its own Let's Encrypt certificate through a DNS-01 challenge that the control plane publishes only for that device.
   - **Relay side:** the relay routes by SNI and forwards bytes without decrypting.
   - **Why:** this is the only option that gives a single toggle, nothing installed on the visiting device, and TLS ending on the Mac, at a relay budget of roughly $12–$108 a month plus traffic for 100–10,000 Macs.
   - **Prototype:** frp's HTTPS forwarding or a small Go SNI router with an in-process client.
   - **Before launch:** a Let's Encrypt rate-limit override, then a Public Suffix List entry, and Certificate Transparency monitoring of issued certificates.
3. **Evaluate ngrok TLS endpoints (ngrok-go) as the managed fallback.** It is the cleanest in-process fit for the same seam, and its terms allow distributing the agent under our account. End-to-end pricing needs a quote, and its customer-data terms need review for private messages. Pinggy TLS is the second quote.
4. **Don't use** Cloudflare Tunnel. Its edge decrypts private messages, and 10,000 tunnels list at $40,500 a month. Quick Tunnels lack SSE and a stable URL.
5. **Don't use** the Anthropic or OpenAI MCP tunnels either. They serve only their vendor's API surfaces, not claude.ai connectors or browsers.
6. **Leave identity in Bridge.** Managed MCP auth products (Auth0, WorkOS, Stytch, Descope) don't make a Mac reachable, and Bridge's passkey consent and approval levels are already built.

Astra's original ranking, kept for reference: (a) a developer relay prototyped with frp; (b) ngrok TLS and Pinggy TLS quotes; (c) Cloudflare named tunnels only if edge plaintext is acceptable. Point 1 above is added because the sign-in path has never been tested with a real connector, and that test is free today.
