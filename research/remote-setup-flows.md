**Remote setup flows — researched 2026-10-27**

Embedded Tailscale Funnel is the closest available fit for one Mac command, a short browser approval, and nothing on the visiting computer. It does not require the Tailscale Mac app or a macOS VPN profile. Own-domain alternatives need DNS work or access to the user's DNS account. A future Bridge relay can reduce that work to two DNS records while keeping the serving certificate's private key on the Mac.

This is an onboarding supplement to [remote-access-services.md](remote-access-services.md), not another relay comparison. [SPEC §23.5](../design/SPEC.md#235-remote) currently defines `bridge remote on [--via system|embedded]`; **all other Bridge commands and flags below are proposals**, not existing functionality. The repository pins `tailscale.com v1.102.4` and Go 1.27. Tailscale implementation claims were checked against that version. Other providers' current documentation is unversioned unless stated otherwise.

No accounts were created, credentials used, or tunnels run. Timings are **unverified planning estimates**, assuming Bridge is installed and the Mac gateway runs: browser authentication usually dominates, DNS can take much longer, and first-use account screens can change. “One command” includes a command that stays pending while the user completes browser steps. It does not mean zero approvals. All public options leave the visiting laptop needing only its browser or existing HTTP MCP client; the private Tailscale option explicitly differs.

Proposed shared behavior: `bridge remote status` reports provider, canonical HTTPS URL, public/private reachability, pending action with a link, certificate expiry and termination location, and the last reconnect/error. `bridge remote off` stops publication. Provider credentials go through a hidden prompt or protected input file and are retained only as necessary; example `--token …` flags mean user-supplied placeholders, never shipped credentials. Run connector processes under the existing Bridge runtime. Do not create an additional login item merely to enable Remote; surviving logout/reboot depends on Bridge's existing startup configuration.

Every flow must publish the web app, OAuth discovery (including `/.well-known/*`), `/oauth/*`, `/v1/*` and `/mcp` under a consistent origin. Use the dedicated public handler, not an unrestricted local administrative listener. A changed hostname changes OAuth issuer/resource identity and can require new passkey enrollment: WebAuthn credentials are scoped to the relying-party ID. Configure the hostname before enrollment and test discovery, consent, token exchange and streaming from outside the Mac's network. These are proposed acceptance requirements, derived from Bridge's design and [WebAuthn's RP-ID rules](https://www.w3.org/TR/webauthn-3/#rp-id).

**1. Tailscale: embedded tsnet, public Funnel or private access.**

**Minimal public flow, approximately 2–5 minutes plus DNS propagation.**

1. On the Mac, run proposed `bridge remote on --via tailscale --name bridge`. Today use `bridge remote on --via embedded`. The proposed `tailscale` choice should explicitly select embedded mode to meet the no-app requirement.
2. Bridge starts its persistent tsnet node and prints/opens the **actual device authentication URL returned by Tailscale**. It typically resembles `https://login.tailscale.com/a/<opaque-value>`; its precise path is not an API contract. Do not substitute a generic signup link or construct the opaque value. Starting tsnet without an auth key produces this URL. See [tsnet authentication](https://tailscale.com/kb/1244/tsnet).
3. A brand-new owner signs in with Google, Apple, GitHub or Microsoft, completes any provider MFA/consent and Tailscale onboarding, and authorizes the named node into the intended tailnet. These are supported identity providers; Microsoft includes personal Microsoft accounts and organizational identities. There is no separate Tailscale password to create. Exact first-run screen order and click count are **unverified** without signup. Existing organization policies can additionally require device/user approval. See [identity providers](https://tailscale.com/docs/integrations/identity).
4. If Funnel prerequisites are absent, Bridge opens the returned enablement link. The owner approves public exposure and HTTPS/certificate-transparency disclosure in the browser. Bridge rechecks and proceeds without another terminal command.
5. Bridge calls `ListenFunnel("tcp", ":443")`, establishes the canonical host, and prints `https://bridge.<tailnet>.ts.net` plus its `/mcp` URL. Tailscale documents up to ten minutes for public DNS propagation. On the other laptop, open that URL: **no Tailscale account, application or command is needed there**. Bridge's own login/consent still applies.

**Defaults and enablement.** MagicDNS is enabled on tailnets created since October 20, 2022. HTTPS certificate issuance requires explicit enablement/CT acknowledgment; treat it as off until verified. Funnel requires a policy grant and per-node publication; it is not automatically public merely because the node joined. The `tailscale funnel` CLI triggers a browser approval that provisions HTTPS and adds the policy permission. The documented default grant permits `autogroup:member`; existing policies can restrict it. Sources: [MagicDNS defaults](https://tailscale.com/docs/features/magicdns), [HTTPS setup](https://tailscale.com/docs/how-to/set-up-https-certificates), [Funnel setup](https://tailscale.com/docs/features/tailscale-funnel).

For an ordinary user-owned node, the enabling policy fragment is:

```json
{
  "nodeAttrs": [
    { "target": ["autogroup:member"], "attr": ["funnel"] }
  ]
}
```

Merge this into the existing policy; never replace unrelated grants. Tagged automation nodes need a matching target, for example `tag:bridge`, and appropriate tag ownership. A permission to use Funnel does not itself open a listener. See the [policy syntax reference](https://tailscale.com/docs/reference/syntax/policy-file).

**What Bridge can automate.** Pinned `ListenFunnel` checks policy access and can fail before establishing the listener; its source explicitly leaves interactive enablement to other code. It does not silently enable the tailnet. Obtain `srv.LocalClient()`, call `QueryFeature(ctx, "funnel")`, and display its `Text`/`URL`. The control server supplies the appropriate enablement URL; do not hard-code `/f/funnel` query parameters. Fallback links are the admin DNS and access-control pages, with `https://tailscale.com/s/https` for HTTPS guidance. Bridge already does the feature query in `internal/remote/system_enable.go`, reused by the embedded backend. Sources: [pinned tsnet implementation](https://github.com/tailscale/tailscale/blob/v1.102.4/tsnet/tsnet.go), [LocalAPI QueryFeature](https://pkg.go.dev/tailscale.com@v1.102.4/client/local#Client.QueryFeature). The returned link's exact first-use combined flow is **unverified**; retain separate HTTPS/policy guidance when necessary.

The node credential cannot grant itself administrative rights. For owners who deliberately supply an administrative API credential, `dns` permits changing MagicDNS through `POST /api/v2/tailnet/:tailnet/dns/preferences`; `policy_file` permits reading, validating and updating `/api/v2/tailnet/:tailnet/acl`. Its documented dependent scopes include `devices:posture_attributes` and `devices:core:read`. Preserve the policy and concurrent changes. A supported API field to enable HTTPS/acknowledge CT was **unverified** in the reviewed API material; do not promise browser-free HTTPS setup. See [API scope/endpoints](https://tailscale.com/docs/reference/trust-credentials).

An owner-created OAuth client uses client credentials to obtain scoped API access, rather than being a consumer “Sign in with Tailscale” consent integration. It can create tagged auth keys with `auth_keys` permission and configured tag rights; supplying only that scope does not confer DNS/policy administration. Creating this client in the admin console is more work than interactive node login. Do not embed a vendor-wide secret in Bridge. See [OAuth clients](https://tailscale.com/docs/features/oauth-clients).

**Auth keys versus interactive login.** `tsnet.Server.AuthKey` supports unattended enrollment. The owner must first generate an auth key, choose its reuse/ephemeral/tag/preauthorization settings, and supply it to Bridge. Prefer a one-use, non-ephemeral key for a persistent Mac when this advanced path is selected. Keys can expire before use; expiry of an enrollment key is distinct from the registered node's key expiry. Preauthorization can satisfy device approval, but neither an auth key nor reusing persisted node state substitutes for missing Funnel policy or HTTPS enablement. Interactive login avoids a secret-copying step for new consumers. Sources: [auth keys](https://tailscale.com/docs/features/access-control/auth-keys), [pinned Server fields](https://pkg.go.dev/tailscale.com@v1.102.4/tsnet#Server).

**System footprint, TLS, limits and cost.** tsnet runs a userspace TCP/IP stack inside Bridge: no root, separate tailscaled daemon, system extension, network-wide interface configuration, Tailscale menu-bar app or VPN profile. Persist its identity in Bridge's protected state directory. It still uses Tailscale's encrypted overlay protocol; “no VPN” here means no OS VPN installation/UI, not absence of tunneling. Public TLS terminates in Bridge on the Mac; the Funnel relay forwards encrypted connections. Funnel accepts only TCP/TLS on 443, 8443 and 10000, only the tailnet's `*.ts.net` names, with non-configurable bandwidth limits whose numeric values are **unverified/unpublished**. An own-domain CNAME is not a supported Funnel custom-domain solution. Sources: [pinned tsnet source](https://github.com/tailscale/tailscale/blob/v1.102.4/tsnet/tsnet.go), [Funnel restrictions](https://tailscale.com/docs/features/tailscale-funnel).

The current **Personal plan is $0 for noncommercial personal use: six users, unlimited user devices, three ACL groups, initially 50 tagged resources, and 1,000 ephemeral-resource minutes/month**. Do not repeat the old three-user/100-device limit for new accounts. Personal identity domains enroll in Personal; organizational domains may enter a business trial, with a personal-use downgrade available when appropriate. Standard lists $8/user/month; legacy plans may differ. Public visitors are not enrolled tailnet users. See [current pricing](https://tailscale.com/pricing).

**The other laptop, private mode.** Proposed Mac command: `bridge remote on --via tailscale --private`. It uses a tailnet-only listener, such as `ListenTLS("tcp", ":443")`, and never enables Funnel. Proposed other-laptop command: `bridge connect bridge.<tailnet>.ts.net:443 --listen 127.0.0.1:8443`. Start a second persistent tsnet `Server`, show its login URL once, join the same tailnet (or establish explicitly permitted sharing), and forward accepted loopback TCP connections through `Server.Dial(ctx, "tcp", target)`. This transport is supported; tsnet does not require a system VPN on either device. Allow about 1–3 minutes for second-device authorization. Tailnet access controls must permit the connection. See [Dial](https://pkg.go.dev/tailscale.com@v1.102.4/tsnet#Server.Dial) and [ListenTLS](https://pkg.go.dev/tailscale.com@v1.102.4/tsnet#Server.ListenTLS).

That raw forward is **not yet a complete browser onboarding design**: browsing `https://localhost:8443` presents a certificate for the tailnet name, not localhost. A local HTTP reverse proxy can validate upstream TLS with the original ServerName, but then origin-bound passkeys, redirects and OAuth issuer URLs need explicit support. A `--socks5` variant with client-side proxy configuration could preserve the original HTTPS hostname and Mac TLS endpoint; the SOCKS implementation and browser/MCP compatibility are **unverified product work**, not a built-in tsnet browser feature. Do not solve this by disabling certificate checks. A local CLI client that supports a custom dialer is simpler. Hosted MCP clients do not inherit this laptop's localhost proxy. Thus “one command on each computer” is feasible for transport, not yet demonstrated for every browser/connector.

**Services and failure modes.** Tailscale Services supplies a stable private service name/TailVIP and can separate service identity from a host. Service hosts require tagged identity and approval or auto-approval; `ListenService` is available in the pinned tsnet version. It adds administration for a single Mac and does not by itself establish a public Funnel/custom domain; public Services/Funnel integration is **unverified** here. See [Services](https://tailscale.com/docs/features/tailscale-services). Diagnose wrong tailnet, pending device approval, removed Funnel grants, disabled HTTPS, certificate issuance throttling, node expiry, DNS delay and Mac sleep separately. Restoring an old identity is preferable to repeatedly creating new nodes/certificates.

**2. ngrok: bring your own account.**

**Minimal free flow, approximately 2–5 minutes.** Run proposed `bridge remote on --via ngrok`; Bridge opens ngrok signup/dashboard, the user creates an account and copies their **agent authtoken** into Bridge's hidden prompt. An explicit form could be `bridge remote on --via ngrok --token …`. Start an embedded Go agent and bind the assigned development-domain endpoint, then print the URL. No standalone ngrok installation is necessary: the official Go SDK supports in-process forwarding/listeners. Current examples use `golang.ngrok.com/ngrok/v2`; select and pin a release when implementing, since this repository has not integrated it. Sources: [Go integration](https://ngrok.com/download/go), [authtoken versus API key](https://github.com/ngrok/ngrok-docs/blob/main/gateway/agent/config/v2.mdx).

The free account has one automatically assigned, stable dev domain, up to three online endpoints/agents, 1 GB outbound/month and 20,000 HTTP requests/month; raw TLS endpoints are excluded. HTTPS is available with provider-managed certificates. Free tunnels do not have a session timeout. **The browser warning still matters:** HTML visits receive an interstitial, with “Visit” suppressing it for seven days. Ordinary programmatic API requests are documented as exempt. A client can send `ngrok-skip-browser-warning: 1`, or a nonstandard User-Agent, but Bridge cannot add that request header before a browser first reaches ngrok. OAuth consent navigation can therefore encounter an extra page; it is not proof every MCP client fails. A paid plan removes it reliably. Source: [free limits and warning bypass](https://ngrok.com/docs/pricing-limits/free-plan-limits).

**Own domain, approximately 5–15 minutes plus DNS/certificate issuance.**

1. User upgrades to **Pay-as-you-go**, owns `bridge.example.com`, and runs proposed `bridge remote on --via ngrok --domain bridge.example.com`.
2. Either the user adds that domain in the ngrok dashboard, or Bridge creates it via the management API using a separately supplied **API key**. An agent authtoken alone is insufficient for management API calls.
3. Bridge displays the returned `cname_target`; the user adds `bridge.example.com CNAME <returned-target>.ngrok-cname.com` at their DNS provider. Use the exact returned target, not an invented global name. DNS automation requires an additional DNS-provider authorization.
4. Bridge polls DNS/domain status and starts the endpoint. For normal HTTPS endpoints, ngrok manages the public certificate and decrypts traffic at its edge. The other laptop opens the URL normally. See [custom-domain steps](https://ngrok.com/docs/gateway/domains/custom-domains) and [domain creation API](https://ngrok.com/docs/api-reference/reserveddomains/create).

**TLS on the Mac.** Offer a separate proposed `--tls passthrough` mode: reserve the domain, start a `tls://bridge.example.com` endpoint without cloud `terminate-tls`, and forward to a Bridge TLS listener. ngrok documents `ngrok tls 443 --terminate-at upstream --url tls://app.example.com` and the equivalent Go forwarding pattern. The Mac must obtain/renew a publicly trusted certificate, for example via DNS-01; the agent authtoken does not authorize the user's DNS. Provider-managed HTTPS followed by HTTPS to the Mac is two TLS connections, not passthrough. Do not upload the Mac's private key to ngrok for this mode. Sources: [TLS termination options](https://ngrok.com/docs/gateway/domains/tls-termination), [ACME DNS-01](https://letsencrypt.org/docs/challenge-types/#dns-01-challenge).

Bridge can create domain resources and certificate-management policy with the API key, then create its live agent endpoint using the authtoken and SDK configuration. Account creation, payment, first credential issuance and external DNS remain user actions unless separately authorized. API automation does not bypass paid feature eligibility. Exact raw-TLS billing/entitlement for the selected account should be checked before promising a price; the full end-to-end invoice is **unverified**.

**Footprint, cost and failures.** Only Bridge plus embedded ngrok state; no VPN profile, menu-bar app or extra login item. Free costs $0, but current pricing also lists a $5 one-time usage credit: quotas are not a promise of unlimited indefinite free activity. Hobbyist lists $10/month with $10 monthly usage credit and no warning, but **does not support your own domain**. Pay-as-you-go lists $20/month with $20 credit plus excess usage; own-domain activity is $0.01/active hour (about $7.30 for 730 active hours, a usage component rather than a complete bill). Sources: [pricing](https://ngrok.com/pricing), [billing limits](https://ngrok.com/docs/pricing-limits). Failures include exhausted quota/credit, token revocation, domain reservation mismatch, DNS/CAA delays, consent interstitials, edge policies accidentally adding another login, and streaming interruption during reconnect. HTTP-mode edge plaintext includes messages, bearer tokens and OAuth traffic; raw passthrough changes that boundary.

**3. Cloudflare: bring your own account and domain already on Cloudflare.**

**Minimal flow, approximately 3–10 minutes with an active zone.** Run proposed `bridge remote on --via cloudflare --domain bridge.example.com`. The user signs into Cloudflare and creates a scoped API token, pasting it into Bridge. Request **Account → Cloudflare Tunnel → Edit** for the chosen account and **Zone → DNS → Edit** for the chosen zone. The API describes Tunnel Write (or the newer connector-specific write permissions) and DNS Write. With supplied account/zone IDs these cover the documented creation flow. For convenient hostname-to-zone discovery, additionally request **Zone → Zone → Read** and use List Zones; avoid demanding broad account access just to avoid asking for IDs. Sources: [tunnel API guide](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel-api/), [List Zones permissions](https://developers.cloudflare.com/api/resources/zones/methods/list/).

Bridge then performs the documented API sequence:

1. `POST /client/v4/accounts/{account_id}/cfd_tunnel` with `{"name":"apple-bridge","config_src":"cloudflare"}`; retain returned tunnel ID and run token.
2. `PUT /client/v4/accounts/{account_id}/cfd_tunnel/{id}/configurations` with an ingress entry mapping `bridge.example.com` to Bridge's dedicated loopback public handler, followed by `{"service":"http_status:404"}`. See the [configuration API](https://developers.cloudflare.com/api/resources/zero_trust/subresources/tunnels/subresources/cloudflared/subresources/configurations/methods/update/).
3. `POST /client/v4/zones/{zone_id}/dns_records` creating a **proxied** CNAME from `bridge.example.com` to `<id>.cfargotunnel.com`.
4. Start `cloudflared tunnel --no-autoupdate run --token-file <protected-file>` and verify the public origin. The run-token file requires cloudflared 2025.4.0 or later and is distinct from the account management API token. See [API setup](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel-api/) and [run parameters](https://developers.cloudflare.com/tunnel/reference/run-parameters/).

After the token is supplied, these steps need no dashboard tunnel wizard or `cloudflared tunnel login`. Keep the run token for reconnect; retain the management token only if the user wants future DNS/tunnel management. A pre-created tunnel run token can start a connector but cannot create the account's tunnel/DNS configuration. Creating an Access application is a separate step and is deliberately omitted.

**Process versus embedding.** The documented client is `cloudflared`, a Go command-line program with Apache-2.0 source. A stable supported in-process Go tunnel SDK equivalent to ngrok-go/tsnet was **unverified**. Recommend bundling a pinned helper with Bridge and supervising it; this still introduces a helper executable and must be described honestly. Reusing internal packages would couple Bridge to upstream internals and requires engineering validation. No WARP client, VPN profile or menu-bar app is required. Foreground child execution needs no separate service install; an independent `cloudflared service install` would add a launch service and falls outside the proposed minimal flow. See [official client repository](https://github.com/cloudflare/cloudflared).

**SSE and public authorization.** Use a named tunnel. Cloudflare documents that `Content-Type: text/event-stream` makes `cloudflared` stream instead of buffer. Bridge should also flush each event, send periodic heartbeat comments, set `Cache-Control: no-cache, no-transform`, bypass caching for authenticated/dynamic routes, and verify both GET SSE and streaming POST `/mcp`. Those additional settings are proposed application safeguards, not a claim that a single header solves every timeout. Quick Tunnels do not satisfy the SSE requirement. See [buffering guidance](https://developers.cloudflare.com/tunnel/troubleshooting/) and [Quick Tunnel limitations](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/).

Do not put an Access login wall, browser challenge, or service-token requirement in front of discovery, DCR, token exchange or `/mcp`: generic clients cannot complete a second provider-specific login. Keep Bridge's authorization. Inspect existing wildcard Access applications and security rules; if one covers the hostname, the user must adjust it in the dashboard or explicitly grant the extra Access-management permissions. The minimal tunnel/DNS token does not promise authority to change Access or WAF settings. An unauthenticated external probe must see Bridge's expected metadata/401 response rather than an HTML Cloudflare login or challenge.

**TLS, visibility, costs and failures.** Visitor TLS terminates at Cloudflare; the tunnel to `cloudflared` is separately encrypted. An HTTPS origin encrypts another hop but does not hide request/response plaintext, message content, bearer tokens, cookies or OAuth exchanges from Cloudflare's edge. This statement concerns technical access, not a claim that Cloudflare retains every payload. Sources: [SSL connection model](https://developers.cloudflare.com/ssl/concepts/), [Tunnel overview](https://developers.cloudflare.com/tunnel/). Named Tunnel is available on the Free plan; domain registration is separate, and optional paid rules/certificates can add cost. Use a first-level hostname such as `bridge.example.com`; deeper names can require additional certificate coverage. Failures include wrong token scope/account, existing conflicting DNS, inactive zone or certificate, outbound port 7844 blocked, helper crashes, buffering, Access/WAF interception and Mac sleep. DNS/Universal SSL delays can extend setup beyond the estimate. No software is needed on the other laptop.

**4. Own domain pointing at a future Bridge relay.**

This is a **proposed architecture**, not a deployed service or verified Bridge feature. Expected setup is 3–10 minutes of user work plus DNS propagation/ACME issuance; operating price and service availability are **unverified**. Proposed command: `bridge remote on --via relay --domain bridge.example.com`.

The command enrolls the Mac with our relay, obtains unique routing/validation targets, and displays exactly two records. For example, assuming the selected hostname is `bridge.example.com`:

| DNS owner name | Type | Value, supplied by Bridge |
|---|---|---|
| `bridge.example.com.` | CNAME | `device-7f2.ingress.relay.example.` |
| `_acme-challenge.bridge.example.com.` | CNAME | `device-7f2.validation.relay.example.` |

`relay.example` and the device ID are illustrative placeholders, not live infrastructure. Use DNS-only records, not an HTTP CDN proxy. The user adds them in their DNS dashboard and returns to the waiting command. Bridge verifies both against authoritative DNS, creates the ACME account/certificate private keys locally, asks the relay control plane to publish the challenge TXT at the delegated validation target, completes issuance, and starts an outbound tunnel. Public SNI routing passes the original TLS bytes to Bridge. The other computer opens `https://bridge.example.com` with no client installation. Let's Encrypt explicitly supports CNAME/NS delegation for DNS-01; our ACME integration must follow that delegation when publishing TXT. See [DNS-01 delegation](https://letsencrypt.org/docs/challenge-types/#dns-01-challenge).

Two CNAMEs are sufficient for the proposed subdomain flow, provided no conflicting records or restrictive CAA policy exist. Choose a subdomain rather than a zone apex, where ordinary CNAMEs conflict with apex records. Existing CAA restrictions may need amendment to authorize the selected CA. No wildcard certificate is needed. Domain-claim registration must be tied to the authenticated Mac and a unique verification target; a different customer must not be able to attach an already claimed name. Those are design requirements, not completed implementation.

Bridge can automate enrollment, DNS checks, ACME issuance/renewal, SNI-route registration and reconnect. With no DNS credential, the two DNS edits are the unavoidable browser step. An optional DNS integration could make them after provider authorization; that should not be required. Keys and renewal state remain on the Mac; no VPN profile, extra helper or menu-bar app is inherent in an in-process relay client.

**Trust qualification.** Passive relays see SNI, peer addresses, timing and traffic volume, but not the forwarded TLS plaintext. DNS-01 delegation grants the validation-zone operator the ability to satisfy certificate challenges, so “our intended certificate key stays on the Mac” does **not** prove a malicious operator cannot obtain another valid certificate and impersonate the origin. Narrow per-device authorization, issuance monitoring and appropriate CAA/account restrictions deserve design review. Treat this as relay confidentiality under the stated trust model, not cryptographic immunity from a malicious DNS/control plane.

Cost is the user's domain renewal plus a future relay subscription/operating budget; no user price is established. Failure modes are typoed/deleted delegation, DNSSEC/CAA conflicts, ACME throttling, renewal while the Mac is offline, lost local state, duplicate domain claims, stale relay routes, relay outage and Mac sleep. Setup must explain which record is wrong and preserve a usable certificate through transient renewal failures.

**5. SSH-based access: Pinggy and localhost.run, no additional tunnel installation.**

Both use the system `ssh` executable already on macOS. The quick command presupposes a running HTTP listener, here `127.0.0.1:8080`; this is illustrative and must map to Bridge's dedicated public handler. Do not blindly expose the existing local admin port. First SSH use may prompt for host-key trust and creates a `known_hosts` entry. A shipped wrapper should verify host keys through a maintained trust mechanism rather than recommend disabling verification. The tunnel stops when SSH exits; Bridge can supervise it with keepalives/reconnect and display its URL. No VPN profile, provider GUI or extra login item is required. The other laptop uses normal HTTPS.

**Pinggy, approximately 30–60 seconds for a temporary demo.** Run:

```sh
ssh -p 443 -R0:localhost:8080 free.pinggy.io
```

If prompted for a password, the documented free flow accepts Enter. No signup is required for that temporary URL. HTTP-mode HTTPS ends at Pinggy. For a stable URL, the user signs up/upgrades to Pro, obtains an access token, assigns a persistent subdomain to it in the dashboard, and uses `ssh -p 443 -R0:localhost:8080 TOKEN@pro.pinggy.io`. Allow 3–5 minutes for signup/payment. Bridge can wrap this as proposed `bridge remote on --via pinggy`, or `--token …` for the paid identity. Sources: [quickstart](https://pinggy.io/docs/), [persistent-domain flow](https://pinggy.io/docs/persistent_subdomain/).

For an own domain, enter it in the Pro dashboard and add the exact CNAME target shown there, DNS-only. HTTP mode's managed certificate requires the documented Validate/Issue Certificate steps, with up to seven minutes after issuance for activation. In contrast, **TLS passthrough** uses:

```sh
ssh -p 443 -R0:localhost:8443 TOKEN+tls@pro.pinggy.io
```

The Mac must already serve a valid certificate for the public hostname on 8443. Pinggy's `tls` mode routes SNI on public 443 and leaves decryption to the Mac; `tlstcp` and `x:localServerTls` are not equivalent. Bridge could provide proposed `--domain bridge.example.com --tls passthrough` with DNS-01 certificate setup. Using a vendor-owned hostname for Mac-controlled ACME issuance/renewal is **unverified**; own-domain DNS-01 is the grounded path. Sources: [custom domains](https://pinggy.io/docs/custom_domain/), [TLS semantics and command syntax](https://pinggy.io/docs/usages/), [TLS tunnels](https://pinggy.io/docs/tls_tunnels/).

Pinggy Free is $0 with a 60-minute tunnel timeout and random domains. Pro provides persistent/custom domains; its current numeric price was **unverified** because the public pricing response did not expose the selected seat/billing amount. Do not substitute an old price. Sources: [pricing](https://pinggy.io/#pricing), [browser screening](https://pinggy.io/docs/http_tunnels/screening/). Free HTTP screening adds a browser confirmation before consent; programmatic requests are exempt, and Pro removes the screen. A controllable browser-like client can send `X-Pinggy-No-Screen: 1`; that does not fix an ordinary first browser navigation. Actual Bridge client behavior still needs a smoke test. Other failures include expired/free sessions, SSH blocking even on port 443, changed host keys, wrong token-domain association and missing Mac certificates. Automatic paid-account/domain provisioning through a public API is **unverified**; use the documented dashboard flow.

**localhost.run, approximately 30–60 seconds for a temporary demo.** Run:

```sh
ssh -R 80:localhost:8080 nokey@localhost.run
```

This provides provider-terminated HTTPS without installing an agent. The documented `nokey` username skips the SSH-key check for free tunnels, so a fresh Mac needs no key generation or account signup. Paid custom domains still require an SSH key. See the [SSH troubleshooting FAQ](https://localhost.run/docs/faq/). See [basics](https://localhost.run/docs/) and [HTTP forwarding](https://localhost.run/docs/http-tunnels/).

For stable access, budget 3–5 minutes: sign into `admin.localhost.run`, subscribe to Custom Domains, add an SSH public key, and choose an available `lhr.rocks` subdomain (no DNS edits) or an owned name. For `bridge.example.com`, add `_lhr.bridge.example.com TXT <dashboard-domain-ID>` and `bridge.example.com CNAME cd.localhost.run`. Then run `ssh -R bridge.example.com:80:localhost:8080 plan@localhost.run`. The subscription lists **$9/month billed annually ($108/year)**. See [custom-domain setup](https://localhost.run/docs/custom-domains/).

TLS passthrough is available only with Custom Domains; use `ssh -R bridge.example.com:443:localhost:8443 plan@localhost.run` and supply/renew the public certificate on the Mac. Allow an additional DNS/ACME setup interval as above. Provider-issued HTTPS in port-80 mode is not passthrough. See [TLS passthrough](https://localhost.run/docs/tls-passthru-tunnels/). Proposed wrapper: `bridge remote on --via localhost-run --domain bridge.example.com --tls passthrough`. Bridge can generate a dedicated SSH key, print its public part, build the command and supervise it; the user handles subscription, public-key registration and DNS. A supported account-management API to remove those clicks is **unverified**. Failures include key mismatch, free-domain changes, lost SSH sessions, unavailable outbound SSH, subscription expiry and certificate renewal failures. A stable paid URL still needs reconnect supervision.

**6. Router port forwarding plus dynamic DNS, for completeness.**

Allow approximately 15–45 minutes, potentially impossible with the ISP/router. The user reserves a LAN address for the Mac, checks for a reachable public address, creates a DDNS hostname/account, configures updates in the router or Bridge, and manually forwards **TCP 443** to Bridge's TLS listener. Configure host firewall access and obtain a public certificate: DNS-01 avoids opening port 80; HTTP-01 requires reachable port 80 as well. Test from a genuinely external network. Proposed command `bridge remote on --via direct --domain bridge.example.com --ddns PROVIDER` can guide detection, updates and certificates, but cannot generally authenticate to/configure arbitrary routers. Sources: [No-IP router flow](https://www.noip.com/support/knowledgebase/general-port-forwarding-guide), [ACME challenges](https://letsencrypt.org/docs/challenge-types/).

TLS ends on the Mac with no relay. No VPN profile/menu-bar app is required; a separate DDNS updater might add a background service if updates are not integrated. Cost ranges from free DDNS to provider/domain fees and possibly a paid public/static IP; exact offers are **unverified**. Discourage this path because CGNAT, double NAT, ISP inbound filtering, IPv4/IPv6 differences, stale DNS, changing LAN addresses, firewall errors and missing NAT loopback make support difficult. It also exposes the home's address and the Mac directly to unsolicited internet traffic. UPnP/NAT-PMP mapping may work on some routers but is not a universal or silently authorized setup mechanism. Nothing is required on the visiting laptop once public DNS and HTTPS work.

**Recommended default and onboarding order.** Default now to **embedded Tailscale Funnel**, making the no-system-app choice explicit. It already matches Bridge's backend, offers public access without a second-device install, and terminates TLS on the Mac. Phrase the promise as “run one command, sign in, approve the link,” not “zero configuration.” Retain system Tailscale as an advanced existing-install option rather than silently selecting it for users who asked for no VPN UI.

1. Present “Get a public URL” first and complete the embedded Tailscale login/enablement flow within the waiting command. Confirm external HTTPS, OAuth and streaming before reporting ready.
2. Present “Use my own domain” next. Once implemented, prefer the future relay's two-record flow for users who want Mac TLS. Until then offer paid ngrok TLS with explicit certificate setup, or Cloudflare for users who accept edge plaintext and the bundled helper.
3. Offer “Use my existing ngrok/Cloudflare account” with provider-specific credential prompts, DNS checks and accurate pricing. Free ngrok is a trial path with a visible consent-warning caveat.
4. Offer “Keep it private” for users who can run Bridge on the other computer. Ship `bridge connect` only after resolving the canonical-origin/browser story; do not advertise it as a way for hosted MCP clients to reach localhost.
5. Keep SSH tunnels under advanced/no-extra-agent setup, distinguishing the fast demo from stable paid deployment. Keep router/DDNS last as an expert fallback.

The acceptance boundary is a stable, publicly trusted URL and a successful real Bridge consent/streaming session. Transport-library support alone does not verify that full onboarding experience; that runtime result remains **unverified** for these researched proposals.
