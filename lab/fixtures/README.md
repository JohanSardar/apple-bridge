# Synthetic web fixture snapshots

Gateway web scenarios with `huge: true` reuse a verified demo-world template. `fixture: list` also prepares the 540-chat list before browser startup. Other scenarios keep their existing setup path. Templates contain synthetic local simulator data only, in an owner-only `apple-bridge/lab-fixtures-v1` directory below the operating system's user cache directory.

The template key hashes the built gateway binary, the running bridge-lab binary (which runs simapple), the Go toolchain version and the generator inputs. These artifact hashes include schema migrations, capture and read-model indexes, FTS triggers, contracts and simulator/generator code. The inputs include the demo seed, huge flag, fixture name and an hourly UTC clock bucket for relative list dates. A different gateway artifact cannot reuse a previous template, even with identical generator inputs.

A cold build has a separate six-minute setup bound. Fixture demo uploads use complete 64-observation capture units, grouped into requests of up to 4096 observations, with Live Photo pairs kept together. Each request retains the existing 120-second bound. List-fixture HTTP bounds remain unchanged. The source processes stop before the gateway database, blob store and simulator state are copied. Before atomic publication, the first clone must have the same complete stored-record digest, durable simulator files and gateway blob payloads as the stopped fresh source. The record digest streams every stored payload, including tombstones and system source records, through a read-only SQLite connection. Verification runs immediately after copying, before starting the cloned gateway and helper. Live reconnects legitimately advance source-status versions and observation times; runtime tests separately preserve application records and source record IDs. A per-key lock protects publication and copying.

The two most recently used templates per fixture kind are retained, subject to a total cap of 1.5 GiB. The size accounting conservatively uses the larger of apparent file size and allocated blocks, including directory metadata. New retention also requires free cache-volume space, after reserving the entry size, to remain above 16 GiB. The floor reads `APPLE_BRIDGE_MIN_FREE_KB` (15 GiB) plus `APPLE_BRIDGE_TRIM_HEADROOM_KB` (1 GiB). Low space triggers LRU eviction and prevents retaining a new entry. `APPLE_BRIDGE_FIXTURE_FREE_KB` can lower the observed free space for the regression test; it cannot inflate actual free space. Each hit atomically refreshes `last_used` under its key lock. Cache-wide maintenance evicts least recently used entries without deleting an entry currently being copied; a new entry that cannot fit is not retained. Staging directories older than the setup bound are reaped only when their build lock is free. APFS uses `cp -c` copy-on-write clones, with an ordinary file-copy fallback.

Cache hits trust the previously verified manifest and clonefile isolation; they do not rehash every record and blob on restore. The full digest comparison runs once when a template is built.

Each project gets its own writable world and fresh browser enrollment. A mutation in one copy cannot alter the template or a later copy. The first `/list-fixture` request can acknowledge a prepared list; later requests retain the previous fixture reset behavior.

Cold generation, demo ingestion and list preparation are recorded separately in `template_cold_setup_ms`; cache hits retain the original template timings. Current project setup is recorded in `fixture_setup_ms` and `fixture_snapshot` (`cache_hit`, `build_ms`, `copy_ms`, record counts/digests and copy method), including a per-project `setups` array in matrix evidence. After preparation, the browser phase retains its existing 180-second deadline and every product timing assertion. Cold setup time is not reported as product performance.

`WEB-FIXTURE-SNAPSHOT` verifies same-key reuse, record/blob equality, copy mutation isolation, owner-only permissions, changed generator inputs and a separately built gateway artifact causing a cache miss, plus hit promotion, two-per-kind retention, cross-kind byte-cap eviction, stale-staging cleanup and low-space retention refusal. It also compares final stored-record digests from a small demo seeded by one upload and by capture-sized chunks, normalizing only independently allocated record IDs through their native aliases.
