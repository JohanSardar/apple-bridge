# Relay deployment

Build the Rust `ab-relay` for linux/amd64 with `packaging/dev/build-bridge.sh ab-relay x86_64-unknown-linux-musl ab-relay ab-relay` (needs the `x86_64-unknown-linux-musl` rust target and `musl-tools`; the binary is static). Install as `/usr/local/bin/ab-relay`; create system user `ab-relay`, install config under `/etc/ab-relay` (directory 0750), then enable `ab-relay.service`.

The public ciphertext listener is 443. The authenticated TLS control API and outbound device tunnel share port 443 using control-host SNI routing. Configure `APPLE_BRIDGE_RELAY_URL=https://ab.lexaai.tech` on the Mac. `--control-acme` issues and renews the control certificate with the existing DNS-01 implementation. Its account and TLS keys remain mode 0600 under `/var/lib/ab-relay/control-tls/remote`; renewal runs every 12 hours when at most 30 days remain, and TLS adopts replacements without restart.

Cloud DNS uses Application Default Credentials from the VM service account. Project: `excerlock`; managed zone: `ab-lexaai-tech`. Required role if denied: `roles/dns.admin` on that zone (or equivalent custom permissions for record-set list/create/update/delete and changes create/get). The VM also needs the cloud-platform OAuth scope. The deployed ab-relay-dns service account already has the required IAM and scope.

Delegate `ab.lexaai.tech` from Cloudflare to the four name servers reported by `gcloud dns managed-zones describe ab-lexaai-tech --project excerlock`. The delegated zone now has apex, wildcard and control A records for 136.65.0.235. The apex is the trusted control endpoint; device TLS remains on the Mac. Cloud DNS publication waits for the exact TXT value at both public resolvers before accepting an ACME challenge. Each device receives an explicit A record copied from the zone wildcard in the same change as its first challenge; otherwise the challenge creates an empty DNS parent that suppresses wildcard A synthesis. Device A records persist across renewals. Cloudflare and other zones remain untouched.

ACME rate-limit override request: “Apple Bridge assigns a stable hostname per device under ab.lexaai.tech. End-to-end TLS keys are generated and retained on each Mac. Please raise the registered-domain issuance limit for our device enrollment service. We renew only within 30 days of expiration, reuse existing certificates and stable device names, and use Pebble/staging for tests. Expected device count and daily issuance volume: operator to supply before submission.”

Owner-only containment uses `-owner-keys-file /etc/ab-relay/owner-keys` in the systemd command. Create that operator-owned file with only the owner's canonical base64url Ed25519 public key, one key per line. Never copy a relay credential or private key into it. The binary validates configuration before listening and reads it again after signature verification on every enrollment or rotation. Missing, empty or invalid configuration denies admission; existing tunnel credentials remain usable. The legacy JSON state and request formats are unchanged. Keep the flag in the command during rollback: older binaries reject it and stop rather than silently reopening admission. For availability rollback use a previously verified gated binary; do not remove the flag to run an ungated binary publicly. Keep private copies of the prior binary, service definition and state, and retain the latest state across binary rollback so revocations and usage are not reverted.

Challenge admission permits 30 requests and enrollment/rotation together permit 20 requests per socket source per minute. Source tracking is capped at 4096 entries; unknown sources are refused while full. Forwarded headers do not establish source identity. This bounds unauthenticated admission independently of device quotas.

`RELAY-TLS-SPLICE` records the vulnerable relay/1 baseline using a synthetic local CA and genuine paired identities: the splicer observes a seeded feed marker after forwarding all four authentication frames unchanged. Wrong-name, untrusted-certificate and direct pinned mTLS controls reject the splice. Public relay/1 must not carry sensitive replica feeds pending channel binding. Pause affected replicas or configure direct pinned mTLS over a private route with no public reconnect fallback.

Until DNS authority moves off forwarding VMs, any retained permission to issue certificates for allowed hosts leaves operator interception possible. R0 limits admission and replica exposure; it does not make hosted browser TLS operator-proof. Abuse response, retention/deletion and operator visibility notices must be finalized before inviting tenants: the relay sees routing metadata, connection timing and aggregate ciphertext usage, while ordinary passthrough leaves application plaintext on endpoints. Investigate reports against the stable hostname, suspend before disconnecting, retain only necessary incident evidence, and disclose retention and deletion exceptions before launch.

## Parallel domain migration

Use `-zone applebridge.eilmer.si -legacy-zones ab.lexaai.tech -dns-zone applebridge-eilmer-si -legacy-dns-zone ab-lexaai-tech`, retaining the existing state path and `-control-host ab.lexaai.tech -app-host app.ab.lexaai.tech`. Set `-accounts-host app.applebridge.eilmer.si` to advertise the new sign-in origin, and add `-extra-hosts applebridge.eilmer.si=control,app.applebridge.eilmer.si=127.0.0.1:8791,eilmer.si=127.0.0.1:8793`. These are exact SNI routes; no wildcard application route is supported. Prepare certificates and DNS before restarting. The additional routes share the control admission pool.

For the website certificate, configure `-dns-challenge-alias _acme-challenge.eilmer.si=_acme-challenge.site.applebridge.eilmer.si` only after a DNS-only CNAME at the source delegates to that exact target. The primary Cloud DNS provider still enforces its suffix on the target. No Cloudflare token belongs on the relay.

Retain the old accounts service and RP; upgrade both accounts executables to the reviewed immediate-transaction policy, and set `AB_ALLOW_REGISTRATION=true` only on the original service. A second accounts service uses the existing bundled executable, database and secret with `AB_PUBLIC_URL=https://app.applebridge.eilmer.si` and `AB_ACCOUNTS_LISTEN=127.0.0.1:8792` and `AB_REGISTRATION_ORIGIN=https://app.ab.lexaai.tech`. Keep credentials out of deployment artifacts. Configure the existing single control process with `AB_ADDITIONAL_PUBLIC_URL=https://app.applebridge.eilmer.si`, `AB_ADDITIONAL_LISTEN=127.0.0.1:8791`, `AB_ADDITIONAL_ACCOUNTS_URL=http://127.0.0.1:8792`. Both control views share one writer/fence and one policy synchronization mutex. A second control process against the same database is prohibited. Existing sign-in sessions and passkeys stay at their old RP; new-origin passkeys need enrollment.

Serve the staged website on loopback port 8793 only, rejecting HTTP Host values other than eilmer.si. Serve /applebridge/install as text/plain, /applebridge as its index or a redirect, and publish no source or README. Stage the final installer from the combined website and repository-identity tree. Compare the public installer's SHA-256 with that staged file.

Do not claim migration complete until both control hosts, both sign-in RPs, cookie isolation, an existing Mac, unchanged iPhone pairing and a real Claude connection have fresh evidence. Independent security review must cover additional SNI admission, ACME alias ownership, shared account SQLite WAL writes, per-RP credential lookup, session scope and shared-secret use. See ADR 0029.

`node packaging/relay/test_accounts_provisioned.mjs PROVISIONED_ACCOUNTS_BUNDLE` runs the fixture suite without npm. The carrier must be the provisioned Better Auth 1.7.17 bundle; only its public dependency code is reused. The helper replaces the application auth/main sections from current TypeScript sources using Node's built-in type stripping, retaining bundled licenses. It does not update dependencies. Fixture mode exports the application entry points, production mode retains the CLI. Keep carrier/generated bundles outside git. A schema-mismatch diagnostic before the first fresh fixture migration is expected; no production database is used.

Stop both accounts listeners before replacing either executable. Keep the control service and relay stopped during the coordinated transition so no requests reach a mixed old/new transaction mode. Take private consistent SQLite backups through SQLite's backup interface and retain the original files/permissions, secret, service files and executables. Install the same generated accounts executable for both services, set the original explicit registration flag, start both and verify health before reopening control/relay traffic. Record SHA-256 parity for each service's ExecStart target. For rollback stop both upgraded services first, restore the prior executable/configuration for the original origin, disable the new-origin service/routes, and restart only the original accounts writer. Retain the newest database and secret; never restore stale account/device state. Do not run an old deferred transaction executable alongside an immediate-transaction writer.
