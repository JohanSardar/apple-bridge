# Source registration

Operation descriptors live in `<source>_descriptors.go` and register their descriptor function from that file. `operations.go` aggregates the registered functions. SimApple source files register route methods in `sourceRoutes`; the shared server loops over the registry. Source command handlers register in `sourceCommands` in the same source file, including ticket lookup and capture adapters. New source routes must not be added to the server bootstrap.

Native registration is generated by `packaging/dev/generate-source-registrations.py`, called under the native build lock before either SwiftPM or the CLT fallback compiles. Add one `sourceTargets` block in `Package.swift` and `native/Registrations/<Target>.swift` declaring `SessionSources.register<Target>(into:home:labEnabled:)`. The generator derives imports and calls from those target blocks and requires a declaration file for every source. Its output is ignored by git. Existing specialized Reminders, Calendar, Contacts and Usage construction remains in `SessionSources.Builtins`; their declaration functions are empty. New sources use `peer.register`, including its optional blob reader, from their own declaration file. No shared bootstrap edit is needed.

Descriptor registrations carry the exact legacy positions alongside their per-source function. Collection sorts by these positions, then by operation name for new descriptors without reserved positions. New sources append after the legacy sequence. The frozen legacy name fixture includes Messages commands formerly appended by init. Tests check the full sequence, reversed registration order and a new source whose name sorts first.

`features.yaml` keeps the existing flat sequence required by featuregraph. Append a contiguous block of feature entries for each new source; no parser or existing scenario changes are required. T01 changes registration structure only. Existing sim scenarios remain the behavior gate; tools/lint checks the file boundaries.

## Source grants

Each source registers its title, agent availability, read/write grants and optional special grants in `internal/contracts/<source>_grants.go`. Registration feeds the source list, Trust parsing and visibility, OAuth metadata, consent, agent setup and source status grant descriptions. System retains its admin grant and stays unavailable to agents. Write continues to imply read; read-level agents continue to downgrade write requests. Usage retains its existing read default in the web picker.

Both OAuth metadata documents advertise the agent-eligible grants. Consent filters the catalog to requested scopes and groups them under source names. Agent setup uses the same grouped catalog through the authenticated grants endpoint. New sources require no edits to either picker. CORE-SOURCE-GRANTS registers a lab-only source, checks browser consent and agent rendering, CLI validation and record visibility with and without its read/write grants.
