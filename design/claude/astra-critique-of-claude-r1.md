I would not approve this design for implementation yet. The Mac hub and interchangeable replicas are the right architecture, but the draft confuses a replicated projection with complete Apple data, durable command acceptance with reliable side effects, and filesystem notifications with change capture. Several omissions can silently lose changes, misreport sends, or expose data across scopes. Fix the guarantees and validate the Messages adapter before building the registry machinery. This review checks published documentation and implementation evidence for macOS 26; I have not run the proposed adapters on a Mac, and undocumented behavior remains unverified.

1. **[blocker] §§1–3, 6 — “100%” has no defensible definition.** Apple stores and their upstream accounts remain authoritative; the Mac is the bridge’s sole sequencer and command gateway. A four-year calendar projection, omitted Reminders features, and missing attachments are not a full copy. Apple explicitly describes Messages in iCloud as retaining only recently accessed messages locally. **Change:** publish per-source coverage, unsupported fields/operations, hydration state, and freshness. Separate “fully replicated bridge state” from “complete Apple history”; obtain agreement on the latter’s limits. [Apple’s storage description](https://support.apple.com/en-mide/guide/icloud/mma17ed475f7/icloud).

2. **[blocker] §4 — Snapshot tagging is not snapshot consistency.** Paging a changing mirror and attaching a sequence afterward can omit records permanently. Server mirror updates and log appends are not explicitly atomic either. **Change:** commit both together; materialize a consistent snapshot at sequence S, retain changes after S, stage pages in a separate replica generation, validate completion, then atomically replace the old generation and cursor. Replacement must remove records absent from the snapshot. Specify interrupted snapshots and the race-free transition from catch-up to live delivery.

3. **[major] §4 — Cursor and epoch rules leave recovery holes.** Per-record version checks cannot justify advancing past missing changes to other records. Restoring an older server backup can reuse sequences without rebuilding “from scratch.” **Change:** define ordered batch coverage, durable acknowledgments, filtered-stream watermarks, and valid cursor bounds. Rotate epochs on rollback/history discontinuity; never compare record versions across epochs. Specify tombstone collection, snapshot expiry, byte limits, and slow-consumer disconnect/resnapshot behavior. Exactly-once applies only to transactional replica state application, not delivery or Apple effects.

4. **[blocker] §5 — The idempotency promise lacks durable boundaries.** Two executors, ledger deletion, or a mirror rebuild can defeat “never executed twice.” A duplicate UUID with different arguments is unspecified. **Change:** enforce unique command IDs, bind them to the authenticated principal and canonical request hash, reject mismatches, and atomically claim execution. Preserve the deduplication ledger independently of change-log retention and mirror rebuilds. After dispatch, never retry an ambiguous effect automatically. Document the unavoidable crash window between Apple’s effect and recording its result.

5. **[blocker] §§5, 6.1 — Observation does not establish causality or delivery.** Two identical texts, including one sent manually, can satisfy the same matcher. `error = 0` means no recorded error, not recipient delivery. **Change:** persist pre-dispatch evidence, route, payload fingerprint, and candidate IDs; correlate conservatively. Distinguish locally observed, delivered, and failed delivery. Verify updated values and deleted-object absence, not mere existence. Allow `unknown` to resolve when stronger evidence arrives, retaining its audit history. Return a commit sequence so callers can wait until their local replica contains the result.

6. **[major] §5 — Expiry and transport errors are underspecified.** A command accepted before its deadline may execute hours later; losing an HTTP response does not prove rejection. **Change:** check expiry and current authorization immediately before dispatch, including after wake/restart. Define server UTC deadlines, maximum TTL, skew handling, and monotonic in-process timers. Return an indeterminate acceptance outcome when necessary and recover using the original command ID. Expiry cannot cancel a side effect already dispatched; optional offline queues need durable ownership and bounded storage.

7. **[major] §§3, 5 — Multiple writers silently overwrite each other.** Record versions currently protect replication only. **Change:** require an expected version for updates/deletes, refresh the native object, serialize bridge mutations per object/series, and apply field patches. Reject stale requests with current state. Apple/iCloud writers can still race outside this serialization; disclose that limitation and reconcile afterward instead of promising global compare-and-swap.

8. **[major] §6.1 — The proposed Messages watcher is not a change algorithm.** `ROWID > last` finds inserts; “fields changed” supplies neither a reliable modification cursor nor deletion detection. Chat membership, attachment joins, and download completion also change. **Change:** use read-only SQLite connections with WAL support, short reads, directory/sidecar watcher rearming, debounce, and a polling fallback. Define bounded rescans plus periodic complete reconciliation, including deletions and database replacement. Probe actual schemas rather than assume `date_retracted` exists. Use GUIDs where available; row IDs are database-local scan positions. [Existing watcher implementation notes](https://github.com/openclaw/imsg/blob/main/README.md).

9. **[major] §§3, 6.1 — Text decoding understates the data model.** An attributed body can contain multiple text/attachment components; edits and reactions require additional structures. Plaintext fallback alone loses information. **Change:** adopt or port a tested typedstream parser, preserve undecoded payloads with explicit decode status, and test long Unicode strings, mixed attachments, edited/unsent parts, and reactions. Never silently convert parse failure into an empty message. [Parser and fixtures](https://github.com/ReagentX/imessage-exporter/blob/develop/imessage-database/src/tables/messages/body.rs).

10. **[blocker] §§5, 6.1 — `messages.send` promises unproven capabilities.** Existing group sends, new direct recipients, and creating a new group are different operations; an array of handles does not establish new-group support. Current implementation evidence documents macOS 26 AppleScript success producing an empty, unjoined SMS row. **Change:** ship a tested capability matrix, explicit service routing and iPhone SMS-relay prerequisites, and reject unsupported combinations. Stage attachments securely; track partial text/file sends individually. Validate group creation separately without assuming private-framework functionality is available. [Sending limitations](https://github.com/openclaw/imsg/blob/main/docs/send.md), [private chat-management requirements](https://github.com/openclaw/imsg/blob/main/README.md).

11. **[blocker] §§3, 6.3 — Calendar identity is unstable as proposed.** External identifiers can collide across calendars/accounts; local identifiers can disappear after full sync. A moved occurrence changes its start date. **Change:** assign bridge IDs, persist native aliases scoped by account/calendar, and reconcile identity changes explicitly. Use original `occurrenceDate` for recurrence identity rather than mutable start time, retaining timezone/date semantics. [External IDs](https://developer.apple.com/documentation/eventkit/ekcalendaritem/calendaritemexternalidentifier), [local IDs](https://developer.apple.com/documentation/eventkit/ekcalendaritem/calendaritemidentifier), [occurrence date](https://developer.apple.com/documentation/eventkit/ekevent/occurrencedate).

12. **[major] §§5, 6.3 — Recurrence and window semantics are incomplete.** EventKit exposes `thisEvent` and `futureEvents`, not a native “all” span. Windowed occurrences cannot establish a complete master/exception history. **Change:** mirror observed occurrences, preserve exceptions, and postpone “all” until split-series semantics are tested. Chunk historical queries: EventKit truncates ranges exceeding four years. Distinguish window eviction from upstream deletion; handle all-day dates, timezones, and DST. Include recurring reminders: only the next incomplete instance is obtainable. [Spans](https://developer.apple.com/documentation/eventkit/ekspan), [query limit](https://developer.apple.com/documentation/eventkit/ekeventstore/predicateforevents(withstart:end:calendars:)), [reminder recurrence](https://developer.apple.com/documentation/eventkit/creating-a-recurring-event).

13. **[major] §§6.2–6.3 — Source reset handling is missing.** Contacts history can return `CNChangeHistoryDropEverythingEvent`; EventKit notifications invalidate cached assumptions. Permission failures must not become mass deletions. **Change:** atomically persist Contacts changes with the fetch result’s history token, rebuild on reset, and define unified-contact/group/key policies. Debounce EventKit notifications and refetch; publish deletions only after a successful, complete scan of the relevant scope. [Contacts reset protocol](https://developer.apple.com/documentation/technotes/tn3149-fetching-change-history-events), [EventKit refresh guidance](https://developer.apple.com/documentation/eventkit/updating-with-notifications).

14. **[major] §§3–4, 10 — Years of history and large blobs have no bootstrap plan.** A long scan or video transfer can starve live updates; a metadata cursor does not prove attachment completeness. **Change:** checkpoint history import, prioritize live processing, prevent older backfill from overwriting newer observations, and expose separate metadata/blob progress. Add chunked resumable transfers, digest verification, quotas, disk-full behavior, and reference-aware garbage collection. Model unavailable/offloaded files explicitly. Push-driven transfer scheduling can still require acknowledgments and resume requests; these are legitimate control traffic.

15. **[major] §§2, 8–9 — Generic replication does not generate API semantics.** JSON Schema cannot define authorization, conflict behavior, useful searches, or MCP tool quality. Additive collections still need discoverable schemas and indexes. **Change:** version wire protocol, collection schemas, and operations separately; negotiate capabilities, define unknown-field/enum behavior, and test rolling upgrades and migrations. Describe query/index metadata explicitly. Treat direct SQLite as a versioned read-only view contract, not a promise to freeze internal storage forever.

16. **[blocker] §§5, 7–8 — Scopes are not enforced across every data path.** Publishing every `system.command` can leak message contents to a reminders-only client. A full replica cannot hide its database from another process running as its owner. **Change:** separate trusted replica identities from scoped API callers; filter snapshots, changes, search, blobs, command arguments/results, and MCP consistently. Derive `client_id` from authentication. Version subscription scopes and handle backfill/purge on scope changes. Document that local file access bypasses API scopes and revocation cannot erase previously copied data.

17. **[major] §7 — “The user’s own machine” is not an at-rest security design.** This exports years of messages beyond Apple’s protections. **Change:** require or explicitly provision OS disk encryption, restrictive file permissions, protected credentials, authenticated localhost APIs, and browser-origin/DNS-rebinding defenses. Specify pairing identity binding, expiring rate-limited codes, key rotation, authenticated blob access, and backup/log redaction. Cover SQLite WAL, indexes, attachments, and command storage too. A custom database-encryption subsystem can wait; the deployment requirements cannot.

18. **[major] §§9–10 — Packaging and sleep need an executable deployment plan.** Signing alone does not grant FDA, Automation, Contacts, or Calendar/Reminders access. **Change:** provide a signed/notarized app, foreground permission onboarding, stable identity, and `SMAppService` registration. Test the actual background process and upgrade path. Request full Calendar access, not write-only access. Explicit sleep, logout, shutdown, and FileVault pre-login remain outages; expose stale reads locally and use a supported sleep assertion while serving. [Service registration](https://developer.apple.com/documentation/servicemanagement/smappservice), [responsible-code considerations](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).

19. **[major] §§10–11 — Health timestamps and happy-path tests are insufficient.** A fresh successful query can still miss mutations. **Change:** measure capture/apply lag, scan coverage, reconciliation drift, oldest pending command, unknown outcomes, and blob backlog. Replicas must detect disconnection independently because an offline Mac cannot publish its own failure. Test snapshot interruption, retention races, restored backups, duplicate payload mismatches, identical concurrent sends, permissions disappearing, recurrence exceptions, clock jumps, and disk exhaustion. Benchmark reconciliation against a multi-year database; ten-minute full scans are an unvalidated default.

20. **[minor] §§8–9, 12 — Simplify tooling, not correctness.** Swift plus SQLite/GRDB fits the native adapters; Go fits an independently installable replica. TypeScript’s relationship to one assistant is irrelevant. Verify SQLite/FTS packaging before promising static cross-platform binaries. Keep WebSocket: SSE plus command POSTs is equally push-based, but switching buys no correctness. Share framing/application logic with local SSE. Generate types and validation first; hand-write useful operations. Defer broad codegen, optional offline queues, new-group sending, and speculative later-source adapters until one complete replication/write path passes failure tests.

**Agree with**

- One Mac gateway, equal replicas, local reads, and no assistant-specific dependency.
- Full-state records, transactional SQLite application, and rebuildable mirrors.
- Durable commands, explicit uncertainty, no automatic retry after ambiguous dispatch.
- Native change hints backed by reconciliation; REST and MCP sharing operation implementations.

**Questions for the user**

- Is complete locally available data acceptable when Apple has not downloaded older history, or is verified cloud-history hydration a release requirement?
- What calendar history/future coverage and attachment disk budget are required?
- Must v1 create new groups, or are existing groups and new direct recipients sufficient?
- Does message success mean local submission or recipient delivery, and what latency target applies while the Mac is awake?
